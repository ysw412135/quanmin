## 二、离"有服务、有建议、有转发的产品"还差什么

当前落地版是"能跑的原型"，不是"能给人用的产品"。差距：

### 1. 🔴 摘要患者看不懂（最大问题）
实测生成的摘要长这样：

```
已报告事实
dominant_sensation: unclear
vomiting_character: none
blood_or_black_stool: no
```

**全是英文机器 key**。普通患者看不懂，也转述不了。而线上 v5（zhengzhuang.html）输出是"主诉：胃不舒服 / 大便：拉稀，肛门不烧"这种中文一行行。FDE 引擎存的是结构化 fact，但**缺一层中文渲染**。→ 落地必须补：fact key + value → 中文短句的映射层（引擎选项里本来就带 label 中文，直接可复用）。

### 2. 🔴 缺医生向的内容组织
v5 已有的"医生可能重点确认 / 六经方向线索 / 舌脉由医生面诊"这三大件，落地版摘要里完全没有。预问诊的价值一半在**让医生 30 秒进入状态**，这部分丢了。

### 3. 🟡 服务形态要选型
落地版是独立 Node 服务（:8787），但老叶线上是 **chat-server.js + cloudflared（laoyetools.com）单点托管**。独立端口意味着多一个要维护的常驻进程 + 多一条 tunnel 路由。且 FDE 引擎本身是**纯 JS 无 Node 依赖**——存在"纯前端化"的可能（引擎直接进浏览器，和 v5 一样零后端）。

### 4. 🟡 "建议"通道在但弱
落地版有留言 tab + `data/feedback.jsonl`，但线上留言已有成熟后台（/quanmin/feedback + admin）。落地版重造了一个，未来两套并存会乱。

### 5. 🟡 转发有但结果不可转发
有"分享/复制摘要/复制链接"按钮（Web Share API），但分享文本 = 英文 fact 串，家人/医生拿到没用。要等中文渲染做好转发才有意义。

### 6. 🟢 已有亮点
移动端优先布局、底部导航、边界说明页、Web Share 兼容降级、合成回归可随时重跑。这些保留。

## 三、推荐的落地路径（三选一，需要老叶拍板）

### 方案 A（推荐）：FDE 引擎纯前端化 → 替换 zhengzhuang.html 的规则引擎
- 把 `src/catalog.mjs` + `src/question-engine.mjs` 移植为浏览器可加载模块（本就是纯 JS）
- 保留 v5 打磨好的中文体验（维度题、六经线索、医生重点确认、复制给医生），**只把"下一题怎么选"从 v5 的固定规则换成 FDE 的信息增益动态选问**
- 零新后端、零新端口、复用现有反馈后台，PWA 可装可分享
- 风险最低：还是静态站，老架构不动；回滚 = 版本号退回

### 方案 B：落地版独立部署（原样上线）
- 8787 独立服务 + 新增 cloudflared ingress（如 laoyetools.com/fde）
- 好处：后端 API 可接真 LLM、数据留服务端
- 代价：多一个常驻进程要维护；摘要英文层不修一样没人用

### 方案 C：先不动线上，把这份评估和引擎源码当资产归档
- 继续用 v5，FDE 只作为知识资产（同昨天"中医症状助手"的入库决定）

## 四、无论选哪个方案都该做的优化（已列）

1. fact key/value → 中文短句渲染层（摘要 + 分享文本）
2. 摘要加"医生可能重点确认 / 六经方向线索 / 舌脉面诊提示"三大件
3. 复用现有 /quanmin/feedback，不重造留言轮子
4. PWA manifest + service worker，让"发给家人"能装桌面
5. 移动端真机验证（X 上那台 iPhone 实测分享面板）
